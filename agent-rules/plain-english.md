# Plain English communication

Apply these rules to user-facing messages and project prose. They adapt
ISO 24495-1:2023 and selected ASD-STE100 Issue 9 principles for software work.

These rules do not establish formal compliance, certification, or ASD endorsement.

## Reader outcomes

Make every message:

- Relevant: Include only information needed for the reader's current task.
- Findable: Put the answer, result, or required action first.
- Understandable: Use familiar words, explicit meaning, and simple grammar.
- Usable: Make the next action, decision, or result clear.

## Required behavior

- Write for the reader's current task.
- Lead with the answer, result, current state, or required action.
- Introduce details in a logical order.
- Use headings or vertical lists only when they make information easier to find.
- Keep one topic in each paragraph.
- Use familiar, concrete words when they preserve the exact meaning.
- Define a necessary technical term or abbreviation at first use.
- Use one consistent term for each concept.
- Use active terms from the project's ubiquitous language when it exists.
- Avoid jargon, slang, idioms, figurative language, and culture-specific references.
- Avoid unnecessary synonyms and contractions.
- Prefer active voice and direct verbs.
- Use imperative verbs for procedures, such as `Run`, `Open`, `Choose`, or `Stop`.
- Keep one idea or instruction in each sentence.
- Keep procedural sentences within 20 words when practical.
- Keep descriptive sentences within 25 words when practical.
- Put a required condition before its action.
- Label requirements, recommendations, options, warnings, and assumptions clearly.
- Ask only questions that can change the result.
- Put one question in each numbered question item.
- State a recommendation and its main reason when a choice is important.

## When the reader reports confusion

- Stop any decision or action that depends on the unclear message.
- Restate the point with different, simpler words.
- Define each necessary technical term.
- Give one concrete example when it can remove ambiguity.
- Confirm understanding only when the next action depends on it.
- Do not repeat the same wording and ask whether it is clear.

## Necessary exceptions

- Preserve exact code, commands, paths, identifiers, error messages, quotations, legal text, and interface names.
- Explain exact technical text separately when needed.
- Do not remove a risk, condition, limit, or uncertainty to shorten the text.
- Treat sentence lengths as strong targets, not mechanical limits.
- Prefer technical accuracy when a shorter or simpler alternative changes the meaning.
- Do not apply the complete ASD-STE100 controlled dictionary to general conversation.
- Do not claim ISO certification, ASD endorsement, or full ASD-STE100 compliance.

## Review before sending

Check these points:

- Can the reader find the answer or required action quickly?
- Does the text use the project's agreed terms?
- Does each sentence express one clear idea?
- Are conditions, risks, and next steps explicit?
- Can a non-native English speaker understand each necessary word?

Revise the text when any answer is no.
